# Electron Benchmarks 产品需求文档

版本：0.2

更新日期：2026-10-25

状态：首期实现；完整实体机冷启动链路待验证

## 1. 产品定位

Electron Benchmarks 是面向 AI Agent 的 Electron 基准测量工具，通过固定标准场景测量启动时间、内存和 CPU，支持单版本测试与多版本对比，用于发现性能变化、验证优化效果。人工可直接调用 CLI 并查看简短终端摘要。

产品参考 Chromium 的 [Crossbench](https://chromium.googlesource.com/crossbench/+/HEAD/README.md) 设计，沿用以测试名作为命令入口、重复传入被测目标进行对比，以及用配置文件保存测试设置的方式，并针对 Electron 的基准测量简化操作。

测试入口为 CLI，支持参数和 JSON 配置。默认输出结构化汇总，环境和原始样本按需读取。工具负责测量、校验和统计；表格、图表及 HTML 由调用方按需求生成，工程中不内置页面渲染器或报告插件系统。

分发优先提供 npm 包，ZIP 可作为离线分发的补充，发布渠道暂不锁定。冷启动任务必须固定工具版本和持久运行路径，跨重启继续执行时使用同一份工具。

本文定义调用方式和用户可见行为。进程控制、资源采集及跨重启恢复的实现另行设计。

### 用户与需求

| 用户 | 需要完成的任务 |
| --- | --- |
| AI Agent | 发起测试，检查完成情况和数据完整性，读取指标与版本差异，按需分析原始记录 |
| Electron 维护者 | 比较发布版本或修改前后的构建，判断性能变化 |
| Electron 应用开发者 | 了解不同 Electron 版本在标准场景下的基础表现 |
| 测试贡献者 | 复现测试条件，提供可核对的样本和环境记录 |

结果只对应记录中的场景和环境，不直接代表真实业务应用的表现。

### 产品范围

第一期只支持 Windows。macOS、Linux 列入[后续待办](../Todo.md)。

包含：

- 单版本测试，以及两个或更多目标的对比。
- 精确发布版本号、本地构建路径及两者混用。
- 热启动、冷启动和单窗口空闲资源测量。
- 冷启动的环境检查、重启安排、自启动管理与正常跨重启继续。
- 默认 JSON 输出、简短终端摘要、独立环境记录与原始样本。

第一阶段不包含诊断采集、任意用户应用测试、桌面 GUI、在线服务、持续性能看板、跨机器结果直接对比，以及版本范围或 `latest` 等别名。

## 2. 测试与场景

测试名决定测量内容，场景决定运行条件。同一场景对所有目标使用相同负载和规则。

| 测试 | 场景 | 用户得到的结果 |
| --- | --- | --- |
| `startup` | `warm`：热启动 | 从发起启动至 APP READY、首次可见视频回调的耗时 |
| `startup` | `cold`：系统重启后的首次启动 | 独立重启周期中的相同启动指标及环境记录 |
| `memory` | 单窗口空闲 | 固定观察期内的各进程和进程组内存 |
| `cpu` | 单窗口空闲 | 固定观察期内的 CPU 时间和平均占用 |
| `all` | 全部标准测试 | 依次执行冷启动、热启动、内存和 CPU 测试 |

`startup` 默认使用 `warm`，可通过 `--scenario cold` 单独执行冷启动。`all` 包含冷启动，会涉及系统重启，开始前执行冷启动环境检查并展示完整安排，由用户确认后开始。`--scenario` 第一阶段仅用于 `startup`，其他测试传入该选项时提示不支持。

场景具有版本号。结果保留场景版本，以区分测试负载或测量规则发生变化的结果。

## 3. 调用方式

CLI 名称为 `electron-bench`。以下是产品接口，示例版本号只用于说明输入形式。

### 3.1 单版本与多版本

```powershell
# 单版本热启动测试
electron-bench startup --electron 40.0.0

# 多版本对比
electron-bench startup --electron 39.0.0 --electron 40.0.0 --electron 41.0.0

# 发布版本与本地构建混用
electron-bench memory --electron 40.0.0 --electron "D:\builds\candidate\electron.exe" --repeat 10

# 全部标准测试，包含需要重启的冷启动
electron-bench all --electron 40.0.0
```

传入一个目标时输出单版本结果，传入多个目标时自动生成对比。固定以第一个目标为基准，其他目标分别与它比较；调整参数顺序即可更换基准。

发布版本自动下载并缓存，本地构建直接使用。准备过程不计入测量。工具自动生成目标 ID，并记录版本、路径和构建身份，区分版本号相同的本地构建。

### 3.2 参数

| 参数 | 含义 | 行为 |
| --- | --- | --- |
| `--electron` | 精确版本号或本地可执行文件路径 | 可重复，CLI 测试模式下必填 |
| `--scenario` | 启动场景：`warm` 或 `cold` | `startup` 默认 `warm` |
| `--repeat` | 每个目标、每项测试的正式运行次数 | 正整数；启动每种冷热条件各 20 次，资源测试各 10 次 |
| `--out` | 结果目录 | 省略时生成本次测试的独立目录 |
| `--config` | JSON 测试配置文件 | 与测试 CLI 参数不混用 |
| `--help` | 用法、场景和指标说明 | 不启动测试、不修改环境 |

`repeat` 不含预热。预热设置、正式运行次数和观察期在执行前显示，并写入计划和环境记录。正式运行失败时保留失败记录，不静默补测或无限重试。

路径不存在、版本格式不支持、参数无效或输出目录存在冲突时，在测试开始前报错。已有结果不得被静默覆盖。

### 3.3 配置文件

```powershell
electron-bench --config benchmark.json
```

```json
{
  "test": "startup",
  "electrons": ["40.0.0", "D:/builds/candidate/electron.exe"],
  "scenario": "warm",
  "repeat": 30,
  "out": "./results/startup-warm"
}
```

配置与 CLI 表达相同的测试。`electrons` 数组顺序决定基准，无需用户填写目标 ID 或基准字段。配置提供 JSON Schema 校验和编辑器提示。

## 4. 普通测试行为

热启动、内存和 CPU 测试在当前会话内完成：

1. 校验参数与环境，下载或定位被测版本。
2. 显示测试内容、全部目标、基准、运行次数和输出位置。
3. 按场景规则预热并测量，持续显示进度。
4. 每完成一次运行立即保存记录。
5. 清理被测进程，生成结构化汇总。

多目标逐个执行，按轮次轮换顺序，避免并发争抢资源。`all` 中各项测试分别运行，启动计时期间不附带内存或 CPU 轮询。

`all` 在开始前完成全部目标准备和冷启动环境检查，并一次性确认完整测试及重启安排。先完成冷启动，再在最后一次开机内执行热启动预热和正式测量，最后执行内存、CPU 测试。避免先运行整批热启动或资源测试，改变冷启动的历史条件。`--repeat` 对每个目标的每项测试分别生效。

同一批次固定部署路径、预检和执行顺序。计划记录完整顺序，不将先冷后热与先热后冷的历史批次合并统计；先冷后热也不表示没有既往运行或系统预取历史。

## 5. 冷启动行为

### 5.1 调用与开始确认

```powershell
electron-bench startup --electron 40.0.0 --electron "D:\builds\candidate\electron.exe" --scenario cold --repeat 10 --out ./results/startup-cold
```

命令首先检查环境和准备文件，不立即重启。检查通过后显示执行安排：

```text
测试：startup / cold
目标：40.0.0、本地构建 candidate
基准：40.0.0
正式运行：每个目标 10 次，共 20 次
重启后测量周期：20 个
继续方式：每次重启并登录后自动继续
环境变更：为本任务设置临时自启动，完成或取消后清理
输出：./results/startup-cold

确认开始后，将安排第一次重启。
```

用户确认前不创建自启动项、不重启。用户拒绝则退出，保留已下载的版本缓存。`all` 使用相同的确认流程，并同时列出热启动、内存、CPU 和冷启动的运行安排。

准备阶段把工具及其依赖、Node 运行时复制到本次结果目录的 `tool/`，固定版本与路径并写入记录。冷启动结果目录须在工具安装目录外。后续自启动使用该副本，不重新解析最新版本；启动计时后再完整校验工具与被测产物，避免测量前读热文件。

### 5.2 环境检查

环境检查分为开始前检查和每次重启后的就绪检查。

| 时机 | 检查内容 | 未通过时的行为 |
| --- | --- | --- |
| 开始前 | Windows 支持、重启与自启动条件、普通账户的独占且未锁定交互桌面、目标与输出位置可用性 | 停止并列出原因，不重启 |
| 每次恢复 | 当前任务与进度有效、已进入新的系统启动周期、工具版本与持久运行路径一致、配置与目标未变化 | 终止测试，保留记录，不重复测量 |
| 正式测量前 | 开机至少 120 秒，连续 3 次总 CPU ≤10%，采样间隔 2 秒；最长等待 20 分钟 | 超时则终止，不生成有效性能样本 |
| 测量前及运行期间 | 控制器和实际 Electron 进程的 CPU、IO、内存优先级符合 Normal / 2 / 5 | 不符合时终止，受影响记录标为无效 |

主测试流程只检查环境，不修改自动登录、电源、安全或系统预取设置。需要权限的准备工作与正式测量分开，正式测量使用非管理员测试账户。

未配置自动登录或无法判断时，提示使用 [Windows 自动登录辅助工具](../tools/windows/README.md)，也允许用户每次重启后手动登录继续。主流程不调用启用或关闭操作，配置迹象不代表已验证凭据有效。

上述等待和 CPU 阈值沿用拆分 PR 测量中已使用的规则。首期记录磁盘活动，但不凭空加入未经验证的磁盘阈值。优先级不能仅检查 CPU，也不能用控制器正常代替实际 Electron 进程的检查。

### 5.3 跨重启执行

冷启动口径为系统重启后被测目标的首次启动，不宣称文件完全无缓存。运行记录保留 profile、缓存条件、等待时间和环境状态。

保留 Windows 默认缓存与预取设置，不清除系统启动学习历史。准备阶段每个目标路径只做一次启动预检，初始化 profile；每次正式运行使用初始 profile 的独立副本。预检也会影响历史条件，需计入运行记录。

每个周期按以下顺序执行：

1. 重启并登录后，工具自动恢复本任务。
2. 校验状态，等待环境就绪。
3. 只测量本轮目标一次。
4. 保存结果与下一轮进度。
5. 尚有任务时安排下一次重启；全部结束后清理并生成汇总。

每次重启只测一个目标一次。N 个目标各正式运行 R 次，需要 N × R 个测量周期。多目标按轮次轮换顺序，顺序写入计划。

下载、校验和测试文件准备在第一次重启前完成。恢复后不先启动目标查询版本，也不执行会提前加载被测文件的完整校验。

完整文件校验放在本次测量结束后，校验失败则标记对应样本无效并终止。虚拟机可用于验证流程，但来宾重启不能证明宿主机缓存已清空；环境记录标明虚拟化条件，其数据不能用于验收实体机冷启动表现。

### 5.4 自启动要求

工具管理本任务的临时自启动，用户无需逐轮手动启动测试。完成或取消后清理，仅处理本任务创建的设置。

不使用计划任务。自启动与恢复过程必须保持控制器和被测进程正常的 CPU、IO、内存优先级，不能因启动方式改变测量条件。具体机制不在本 PRD 中规定。

### 5.5 中断与清理

环境检查超时、测量失败或状态异常时终止测试，停止后续重启，清理自启动设置。已保存的样本保留，未完成或失败的运行不计为成功样本。

用户在当前终端通过 `Ctrl+C` 中断测试，也可在结果目录创建 `STOP` 空文件。每次重启前倒计时 15 秒，期间同样可以停止。重启不强制关闭其他应用，若 Windows 未在 60 秒内完成重启则终止，不自动重试。工具保留已有数据并输出未完成结果。

正常的跨重启继续属于冷启动执行流程，首期必须支持；异常中断后的断点续测不在首期范围内。再次测试需要重新发起，使用新的运行记录。

清理失败时，显示未清理的设置及处理办法。后续再次登录不得因残留自启动而重新开始已结束的测试。

## 6. 任务状态与异常

stderr 显示准备、等待和测量进度，结束后标明已完成、已中断或失败，以及清理是否成功。同一机器一次只允许一个测试任务，新测试遇到尚在执行的任务时拒绝启动。

| 情况 | 产品行为 |
| --- | --- |
| 下载、配置或准备失败 | 报错退出，不进入测量或重启流程 |
| 测试进程崩溃或超时 | 保存失败原因并终止，冷启动停止后续重启并清理自启动 |
| 工具退出或系统意外中断 | 保留已有记录，无法确认的运行标为中断；下一次启动时处理残留设置，不自动续测 |
| 已中断后再次登录 | 不重新开始测试或触发下一次重启 |
| 工具版本、持久运行路径、目标文件或测试配置发生变化 | 停止后续测量和重启，说明变化原因；无法自动清理时显示处理办法 |
| 用户重复启动测试 | 提示已有测试正在执行，不启动第二个任务 |
| 平台不支持某场景或指标 | 执行前明确说明，不自动替换成另一种测试 |

## 7. 测量与数据要求

### 7.1 启动指标

沿用“拆分PR合入”会话后期的计时口径：从父进程调用 `spawn()` 紧前的高精度时间起算，包含同步创建进程、加载器与应用初始化的开销。不能从 `spawn()` 返回后或应用 JS 开始时起算，也不能与旧的 Windows 进程创建时间口径混合比较。

| 指标 | 终点 | 指标含义 |
| --- | --- | --- |
| APP READY（默认主指标） | 主进程 `app.whenReady()` 回调入口 | Electron 初始化就绪耗时，不代表页面或窗口可交互 |
| 首次可见视频回调 | 标准页面首次收到有效的 `requestVideoFrameCallback`，在回调入口记时 | 首次观察到的可见视频呈现回调耗时，不代表解码第一帧或物理屏幕输出 |

两个指标来自同一次启动，分别汇总。终点使用事件发生时的时间，而非父进程收到消息的时刻；主进程、渲染进程与父进程的时间必须对齐并通过有效性校验。

启动页面固定为本地 SVG 和 1280×720 静音视频，不访问网络。测量时窗口与页面可见、窗口未最小化、视频未暂停，视频尺寸和帧记录有效。日志写入、截图及资源信息读取安排在启动终点之后，不改变启动计时负载。

原始数据保留计时口径版本，同时记录发起启动至进程创建的区间和 `spawn()` 调用耗时，供核对计时边界。它们不作为额外测试项，不增加用户参数。

### 7.2 预热与统计

启动测试每个目标、每种冷热条件默认 20 次正式运行。热启动每个目标先预热 5 次，预热和正式样本在同一次开机内完成。冷启动在每次重启后直接测量，不在正式样本前启动目标预热；准备阶段的预检另行记录。

启动指标输出 P50、P90、有效样本数和失败数。分位数按排序后的线性插值计算，位置为 `(n−1)×p`。差值和百分比先用未舍入的数据计算，再格式化展示。

汇总按目标、冷热条件和端点分组，保留逐轮数据，不将前期慢、后期突降的变化藏在汇总值中。不仅凭耗时下降认定系统预取学习生效。首期不增加显著性结论；资源测试同样按独立正式运行汇总 P50/P90。

### 7.3 资源指标与原始数据

内存和 CPU 使用固定的单窗口静态页面，不运行启动场景的视频。每个目标先进行 1 次预热、默认 10 次正式运行。页面就绪后静置 10 秒，再观察 20 秒，每秒读取各进程指标，首个 CPU 读数仅用于建立采样区间。

内存主指标为各进程私有提交量之和（MiB），同时输出工作集总和和观察期内采样峰值。私有提交量不是私有驻留物理内存；工作集求和可能重复计算共享页，不能称为去重后的物理占用。保留各进程数据，目标缺失必要指标时明确失败。

CPU 使用 Windows `GetProcessTimes` 的进程累计 CPU 时间差，按实际观察时长与整机逻辑处理器容量归一化，100% 表示全部逻辑核满载，同时输出累计 CPU 秒数。Electron 的百分比读数保留在原始记录中，不直接用于正式 CPU 指标，避免部分构建首个区间出现负值的问题。进程组在观察期内发生变化时拒绝使用不一致的区间。每次独立运行先汇总观察期，再以 P50/P90 汇总正式运行，不把每秒采样当作独立实验。

每次测试保留：

- 工具、场景和结果协议版本，以及实际生效的测试配置。
- 系统、架构、硬件和相关环境条件。
- 各目标版本、路径、构建身份、启动参数和执行顺序。
- profile、缓存、预热、运行次数、采样及观察期设置。
- 每次运行的原始数据、状态和失败原因；冷启动额外记录重启周期与环境检查结果。

失败或不支持的指标不填零。异常值不静默删除，采用剔除规则时保留原数据并说明原因。未完成任务必须输出已完成和计划样本数。

## 8. 输出与数据消费

### 8.1 CLI 输出

测试调用正常退出时，stdout 只输出一个 JSON 对象，与本次的 `summary.json` 内容一致；准备失败、尚未建立运行记录时输出结构化错误对象。`--help` 输出纯文本用法，不执行测试。

进度、交互提示和简短终端摘要写到 stderr。stderr 有内容不表示失败；调用方依据退出码和 JSON 判断结果，不解析日志文案。

| 输出 | 内容 |
| --- | --- |
| `summary.json` / stdout | 任务状态、数据完整性、显式基准、目标身份、分组指标、样本数量、版本差值、警告及详细文件路径 |
| `environment.json` | 系统、硬件、优先级和实际采用的测量预设 |
| `samples/*.json` | 每次预热与正式测量的结果、有效性和原始数据 |
| `plan.json` | 固定测试配置、目标和完整执行顺序；预检失败时可能尚未生成 |
| `run.json` | 当前运行状态、执行位置、重启次数及失败记录 |
| stderr | 进度、主要指标 P50、失败原因和汇总文件位置 |

汇总不嵌入完整环境或原始数据。文件路径为测量主机上的绝对路径；目录转移到其他机器后由调用方重新定位。新测试不生成 HTML，不修改已有历史产物。

### 8.2 指标与完整性

单版本与多版本共用一个数据结构，按目标和场景分组。首个目标为基准，并在 `baselineTarget` 中显式声明。每组包含计划、有效、失败、未执行数量和缺失指标列表。

指标字典声明单位、含义、主次指标及增减方向。启动边界核对指标标为 informational，不用于自动推断性能优劣。所有正式结果输出 P50/P90，差值统一使用未舍入 P50；绝对差值为目标减基准，百分比为差值除以基准再乘以 100。基准为零时百分比为 null。

“平均 CPU”和“观察期峰值”是单轮观察期的计算方式；P50/P90 汇总各轮结果。缺失指标不补零，也不只汇总少数返回了指标的样本。原始样本中的预热和失败记录保留，不参与分位数。

`dataComplete` 表示正式样本和所需指标是否齐全，独立于执行状态。状态为 complete 但数据缺失时，完整性为 false、退出码非零。每组只有一个有效样本时输出 SINGLE_SAMPLE 警告。百分比变化不等于确认的性能回归，工具不输出显著性结论。

AI 默认读取汇总，检查 `status`、`dataComplete`、`error`、`cleanupError` 和样本量后，再使用指标。需要复核时按 `artifacts` 路径读取环境、计划或逐次样本；跨批次比较仍需核对场景、计时口径和环境条件。

### 8.3 协议和异常

汇总及 stdout 使用输出协议 v2，原始样本保留 v1；提供 [输出 Schema](output.schema.json) 和 [样本 Schema](sample.schema.json)。破坏字段结构或含义时升级协议版本；兼容新增字段不改变旧字段含义，消费者忽略不认识的新增字段，拒绝不支持的协议版本。

错误包含稳定的 `code`、失败阶段 `stage` 和可读的 `message`。没有建立运行记录时 `kind=error`；已有记录的结果为 `kind=result`，即使测试失败也保留已经取得的数据。缺失文件不提供虚假的可用链接。

| 退出码 | 含义 |
| --- | --- |
| 0 | 正常完成、数据完整且清理成功；或帮助命令成功 |
| 1 | 环境、准备、测量、清理或输出失败，以及数据不完整 |
| 2 | 输入错误或输出目录冲突 |
| 130 | 用户拒绝重启或主动中断；如同时清理失败则返回 1 |

冷启动仍需交互终端明确确认。非交互调用提前返回 REBOOT_CONSENT_REQUIRED，不下载、不预检、不设置自启动、不重启。确认提示写到 stderr，stdout 可以交由程序读取。正常跨重启时进程会被系统终止，不能以进程结束判断整个任务完成；重启前保存 waiting-reboot 状态和汇总，最终结果以持久目录内的文件为准。

## 9. 验收标准

| 编号 | 验收要求 |
| --- | --- |
| A1 | 一个目标可完成标准测试，得到汇总、原始样本和环境信息 |
| A2 | 三个目标可在同一测试中运行，分别输出相对首个目标的差值和变化百分比 |
| A3 | 精确发布版本与本地构建可混用，同版本号的本地构建能被区分 |
| A4 | CLI 与等价 JSON 配置产生相同的测试安排 |
| A5 | 默认启动测试为热启动；`all` 按冷启动、热启动、内存、CPU 的顺序执行，并在开始前检查环境、确认重启安排 |
| A6 | 冷启动在确认前不设置自启动、不重启，并展示完整运行安排 |
| A7 | 两个目标各运行 10 次时，安排 20 个独立的重启后测量周期 |
| A8 | 冷启动跨重启自动继续，保留进度，已完成样本不重复计数 |
| A9 | 冷启动不使用计划任务；控制器或实际 Electron 进程的 CPU、IO、内存优先级不符合要求时不产生有效样本 |
| A10 | 环境超时、测量失败或用户中断时停止后续重启，保留数据并清理自启动；首期不提供任务管理命令和异常断点续测 |
| A11 | 完成或取消后清理自启动；清理失败可见，残留设置不会重新开始任务 |
| A12 | 失败、中断、无效和不支持的数据均明确标记，结果不以零值或静默补测掩盖问题 |
| A13 | 冷启动任务使用固定工具版本和持久运行路径，跨重启不重新选择版本；工具变化或不可用时不继续测量 |
| A14 | 第一期仅支持 Windows；虚拟机结果标明环境，不作为实体机冷启动验收依据 |
| A15 | 同次启动输出 APP READY 和首次可见视频回调，均从父进程发起启动前起算，原始数据记录计时口径版本 |
| A16 | 启动默认每种条件 20 次，热启动预热 5 次；P50/P90 可由原始样本按固定方法复算 |
| A17 | 测试 stdout 可直接解析为一个 JSON 对象，进度和终端摘要只写 stderr；新测试不生成 HTML |
| A18 | 单/多版本、启动/全部测试共用输出 Schema；指标带单位和口径，环境与原始样本按需读取 |
| A19 | 数据缺失、单样本、真实零值、零基准和失败/中断在结构化输出中可区分；取消不返回成功 |

## 10. 首期交付约定

- 平台为 Windows 10/11 x64，控制器使用 Node.js 22.12 或更新版本，目标使用 Electron 22 或更新版本。ARM64 与其他平台留待后续验证。
- npm 包名为 `electron-benchmarks`，命令名为 `electron-bench`。npm 分发包含编译后的原生辅助程序，源码构建需 MSVC x64 工具链；本次开发不等于已经发布到 npm。
- 交付结构化汇总、原始样本、环境记录和简短终端摘要；不内置 HTML、图表或报告插件系统。独立离线重算入口、计划预览、ZIP 离线分发列入 TODO。
- 自动登录由独立的 `tools/windows/autologon.ps1` 管理，主流程仅只读检查并提示调用。

开发语言沿用产品方案中的 TypeScript / Node.js；本阶段不展开技术架构。
