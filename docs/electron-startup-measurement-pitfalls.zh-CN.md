# 建设经验：Electron Windows 启动测量

更新日期：2026-10-20

本文记录 Electron Windows EXE/DLL 拆分实验中踩过的四个测量坑，以及当时的原因分析。

## 1. 计时起点要覆盖整个启动过程

早期实验从 Windows 进程创建时间起算，后续改为父进程调用 `spawn()` 紧前记录高精度时间。两者都可以称为“启动时间”，但覆盖的工作不同。

### 原因：发起创建进程到进程创建时间戳之间，也有开销

`spawn()` 不是瞬间得到一个已经运行的子进程。父进程需要准备启动参数、环境和句柄，并调用 Windows 的进程创建接口；系统也需要处理目标可执行文件及进程创建所需的准备工作。不能把这些工作都视为发生在子进程创建时间戳之后。[`GetProcessTimes`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes) 返回的是进程创建时刻，不是父进程开始发起启动的时刻。

设父进程调用 `spawn()` 前为 t0，Windows 记录的进程创建时刻为 t1，应用就绪或视频回调为 t2。旧口径计算 `t2 - t1`，会漏掉 `t1 - t0`；从父进程发起启动计算则是 `t2 - t0`。若等到 `spawn()` 返回才开始计时，还会漏掉调用期间已经发生的子进程启动工作。

这对 EXE/DLL 拆分尤其敏感：大 EXE 与小启动器加 DLL 的结构，可能改变进程创建阶段与后续 DLL 加载阶段各自承担的成本。如果只看 t1 之后，起点之前的差异就不在结果里，不能把后半段变快直接当作用户等待时间减少。反过来，从应用 JS 开始计时还会漏掉启动器、预读和进入 JS 之前的原生初始化。这里也不能说旧的进程创建时间口径漏掉了全部预读或 DLL 加载；那些发生在进程创建之后的工作仍在旧区间内。

后续测量脚本同时保留了 `parentToCreationMs` 和 `spawnCallMs`，用于区分起点前移补进来的区间与整个同步调用区间。父进程 `spawn()` 前的时间仍不是精确的 `CreateProcessW` API 入口，但包含了调用方发起启动的开销。

旧同步预读批次与后来的异步批次还更换了 Electron 基线，所以不能把旧报告约 20 ms 与新报告约 2–4 ms 的热启动开销直接相减，宣称代码优化了十几毫秒。计时边界变化和代码收益不能混为一谈。

## 2. 计划任务的运行条件会影响测量

此前两批测试使用相同产物，冷启动收益却出现明显变化。排查后发现，旧流程通过 Windows 计划任务启动，未显式设置任务 `Priority`，使用默认值 7；新流程改为普通账户的 HKCU Run 登录启动项。两种入口的运行条件并不相同。

### 原理：低 I/O 优先级改变了系统预取条件

按照[微软的任务优先级定义](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-priority-settingstype-element)，任务 `Priority=7` 对应 BelowNormal CPU、Low I/O 和 Low memory；`Priority=4` 才对应三者均为 Normal。这里的任务 Priority 是一组运行条件，不能只理解为 CPU 调度优先级。

当时的启动链中，Electron 子进程继承了这些低优先级条件。本机诊断确认：Low I/O 条件下，Windows 没有执行对应的应用启动预取；恢复 Normal I/O 后，符合条件的启动重新出现了实际预取阶段。

系统应用预取会依据历史读取模式提前批量读取启动所需的页。没有这一步时，基线更多地依赖启动过程中的按需缺页读盘，显式 DLL 预读就显得更有优势。恢复正常启动条件后，基线也获得系统预取，手动预读的相对收益随之改变，还需要重新评估额外读取的成本。因此，旧结果不能直接代表正常交互启动下的收益。

### 验证：只恢复 I/O 优先级即可恢复预取

排查先交叉使用旧、新部署路径进行四次重启跟踪，低优先级下均未发现实际预取阶段，不支持“仅仅是路径变化”的解释。随后固定账户、EXE、路径和应用，读取实际父子进程优先级，再分别只恢复一项属性：

| 单因素干预 | Electron CPU | I/O | 内存 | 实际预取 |
| --- | --- | --- | --- | --- |
| 只恢复 CPU | Normal | Low（1） | Low（2） | 未执行 |
| 只恢复 I/O | BelowNormal | Normal（2） | Low（2） | 执行 |
| 只恢复内存 | BelowNormal | Low（1） | Normal（5） | 未执行 |
| 保持默认条件 | BelowNormal | Low（1） | Low（2） | 未执行 |

ETW 中，未预取时 `ScenarioDecision` 的 `ActionFlags=0`；只恢复 I/O 后出现 `ActionFlags=3` 和对应的预取阶段。另一次对照在开启 WPR 时仍复现了“正常优先级有预取、低优先级无预取”，排除了 WPR 是此次不预取的必要原因。

这些证据确认了本机的机制差异，但没有逐毫秒解释两批历史结果的全部差额，也不表示每次 Normal I/O 启动都必定预取。诊断跟踪使用最小应用，不能代替正式视频场景的性能测量。

### 为什么只调整 CPU 优先级不够

仅设置 PowerShell 的 `PriorityClass=Normal`，看起来已回到“正常优先级”，但 I/O 优先级仍可能保持 Low。上面的单因素实验恰好证明了这一点：CPU 恢复后，系统预取仍未执行。因此，不能只根据任务成功运行、CPU 优先级正常或父进程设置成功，就认为实际 Electron 启动条件与交互启动相同。

后续流程改用普通账户登录启动项，并检查控制器 CPU、I/O、内存优先级为 Normal / 2 / 5；诊断阶段还核对了真实子进程属性。计划任务本身并非一定不能测，问题在于默认 `Priority=7` 悄悄改变了实验条件，显式 `Priority=4` 对应的才是三项 Normal 条件。

## 3. 测试顺序会影响结果

历史实验中，先热后冷与先冷后热的批次表现不同，曾出现先热后冷批次的 SSD 冷启动劣化。这些批次的结果不能直接合并。

同步预读批次还出现过 HDD 改动版 APP READY 从第 10 轮起明显下降的现象。由于没有对应的 ETW 预取事件，原因未单独确认，不能仅根据耗时下降就认定系统学习或预取生效。

### 原因：重启不等于抹掉启动历史

一批热启动不只生成测量数据，也会反复访问同一组文件，可能改变系统缓存和预取学习记录。来一次重启，并不意味着这些历史条件全部恢复原状。因此，“先热后冷”中的冷启动与“先冷后热”中的冷启动，不能仅凭都重启过就视为条件一致。先冷后热也不代表从未训练过：准备阶段的预检、此前的运行历史仍可能产生影响。

这里要区分顺序造成条件变化的风险与某批次的实际根因。前述跨批差异还涉及计划任务优先级、部署路径等变化，不能把全部差额都归因于冷热顺序。HDD 第 10 轮的阶跃也只有现象，没有足够证据确认是预取学习。

基线与候选的先后位置同样可能与后台活动、缓存或系统状态随时间的变化混在一起。始终先跑 A 再跑 C，会让版本和位置绑定；交替 AC/CA 可以减少这种固定位置偏差，但不能保证消除所有干扰。逐轮数据之所以有价值，是因为汇总 P50/P90 会隐藏“前几轮慢、后面突然变快”的过程，单看汇总容易把状态变化误认为代码收益。

## 4. VMware 不能用于验证实体机冷启动数据

此前曾在 VMware 中重启 Windows 来宾系统后测量首次启动，但这只能说明“来宾重启后的首次启动”，不能据此验证实体机冷启动收益。

### 原理：来宾重启没有控制宿主机的缓存

虚拟机内的文件读取还要经过虚拟磁盘和宿主机存储层。重启来宾系统并不等于重启宿主机，也不能证明宿主机对 VMDK 的缓存已失效。如果读取由宿主机缓存满足，来宾看到的缺页或磁盘读取就不能代表底层物理磁盘冷读，拆分和预读的收益也可能随之变化。来宾整机的磁盘计数同样不能直接当作 Electron 的物理读取量。

当时的 VMX 配置与 VMware 日志不足以确认实际宿主机缓存模式。因此，已确认的问题是宿主机缓存没有被控制或验证，不能进一步断言每次测量都命中了宿主机缓存。历史记录还确认虚拟机文件和实体机被测产物位于不同的物理 SSD，不能将两组结果视为相同存储条件下的比较。

### 为什么虚拟机重启数据不能替代实体机冷启动数据

即使虚拟机能完整跑通重启、登录续跑和采样，证明的也是流程可用，不能证明存储读取条件等价于实体机。增加虚拟机样本量或多次重启来宾，也补不上宿主机缓存未被验证这个缺口。此类数据只能按来宾系统的具体条件解释，不能用来验收实体机冷启动收益。实体机重启同样保留 Windows 默认预取历史，也不能写成“所有缓存已清空”。
